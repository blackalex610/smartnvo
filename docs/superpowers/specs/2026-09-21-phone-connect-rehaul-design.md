# Phone Connect Rehaul — Design

Date: 2026-09-21
Status: Approved, ready for implementation planning

## Problem

Connecting a phone today means reading a six-digit code off the desktop and
typing it into `/controller`. The code is generated by the desktop
(`generatePairingCode()`), claimed as a Socket.IO room, and matched by hand on
the phone. It works, but it is slow, error-prone, and nothing like the
zero-friction device list users expect from tools such as LocalSend.

The target experience:

1. A phone that is sitting on the connect screen appears by itself in a list on
   the desktop. Navigating away removes it from the list.
2. The desktop clicks a device. The phone shows a confirmation prompt.
3. On accept, the two are linked. The phone becomes a Kahoot-style companion:
   almost nothing on its screen, everything on the desktop.
4. When an NVO exam starts, the phone shows the list of open-response problems.
   The student photographs a solution and it lands on the desktop as the answer
   image for that specific problem.

## Decisions

Three forks were settled before design:

- **Discovery is account-scoped.** A phone is visible only to desktops logged
  into the same account. Browsers cannot do mDNS or UDP broadcast, so true LAN
  discovery is impossible from a web app; the realtime server holds the presence
  registry instead. The current server already enforces same-account pairing via
  `ownerUserId`, so this is the smallest secure change, and it keeps working when
  the phone is on mobile data rather than the house Wi-Fi.
- **Photos stay on the socket.** Phone to desktop as a base64 data URL, into
  `answerImages[questionId]`, exactly as today. The backend upload stack
  (`mobile_uploads.py`) is not brought into this flow. Accepted consequence:
  images live in `localStorage`, are capped at 8 MB, and are lost if the desktop
  reloads mid-exam.
- **Scope is the pairing stack only.** `companion_pairing.py`,
  `mobile_uploads.py`, `MobileCapturePage`, `LiveUploadsPage` and
  `channel_state_store` are a second, parallel implementation. They are left
  untouched and unreferenced.

## Goals

- Replace code entry with a live device list and an explicit confirm handshake.
- Give the phone a minimal connected state and a problem-photo state.
- Preserve the exam integration contract so `NVOPracticeExamPage` needs no edits.
- Survive the reconnects that phones actually do (screen sleep, Wi-Fi handoff).

## Non-goals

- Pairing across different accounts, or classroom-wide device discovery.
- Server-side persistence of answer photos.
- Phone-initiated pairing (the phone cannot request the desktop).
- More than one phone linked to one desktop at a time.

## Architecture

### Concepts

**Presence** — a phone sitting on the connect screen, announced to the server and
visible to that user's desktops.

**Link** — a confirmed desktop-to-phone binding. Replaces the room/code concept
entirely; `generatePairingCode`, `createRoom` and `joinRoom` are deleted.

### Realtime server state

```js
presenceByUser  : Map<userId, Map<deviceId, PresenceEntry>>
links           : Map<linkId, LinkRecord>
linkByDeviceId  : Map<deviceId, linkId>
linkBySocketId  : Map<socketId, linkId>
pendingRequests : Map<requestId, PendingRequest>
```

```js
PresenceEntry  = { deviceId, socketId, name, platform, userAgent, announcedAt, busy }
LinkRecord     = { linkId, userId, desktopSocketId, phoneDeviceId, phoneSocketId,
                   examProblems, createdAt, desktopGraceTimer, phoneGraceTimer }
PendingRequest = { requestId, userId, desktopSocketId, phoneDeviceId, timer }
```

Presence is keyed by `deviceId`, not `socketId`. The phone mints a UUID once and
stores it in `localStorage` under a user-scoped key. A reconnecting phone
therefore replaces its own entry instead of appearing twice in the list.

### Events

Phone to server:

| Event | Payload | Ack |
|---|---|---|
| `presence:announce` | `{ deviceId, name, platform }` | `{ ok, deviceId }` |
| `presence:withdraw` | — | `{ ok }` |
| `link:respond` | `{ requestId, accept }` | `{ ok }` / `{ ok:false, reason }` |
| `link:leave` | — | `{ ok }` |
| `answer:submit` | `{ problemId, image }` | `{ ok }` / `{ ok:false, reason }` |

Desktop to server:

| Event | Payload | Ack |
|---|---|---|
| `presence:subscribe` | `{ name }` | `{ ok, devices }` |
| `presence:unsubscribe` | — | `{ ok }` |
| `link:request` | `{ deviceId }` | `{ ok, requestId }` / `{ ok:false, reason }` |
| `link:cancel` | `{ requestId }` | `{ ok }` |
| `link:end` | — | `{ ok }` |
| `exam:problems` | `{ problems }` | `{ ok }` |

Server out:

| Event | To | Payload |
|---|---|---|
| `presence:list` | desktops | `{ devices }` |
| `link:incoming` | phone | `{ requestId, desktopName, expiresInMs }` |
| `link:established` | both | `{ linkId, peer, examProblems }` |
| `link:rejected` | desktop | `{ deviceId }` |
| `link:expired` | both | `{ requestId }` |
| `link:ended` | both | `{ reason }` |
| `link:peer-reconnected` | desktop | `{ deviceId }` |
| `exam:problems` | phone | `{ problems }` |
| `answer:submit` | desktop | `{ problemId, image, deviceId, deviceName, submittedAt }` |
| `answer:received` | phone | `{ problemId }` |

Reason codes: `UNAUTHORIZED`, `INVALID_PAYLOAD`, `DEVICE_GONE`, `DEVICE_BUSY`,
`ALREADY_LINKED`, `NOT_LINKED`, `TOO_LARGE`, `REQUEST_EXPIRED`,
`REQUEST_UNKNOWN`.

### Presence distribution

Desktops join the Socket.IO room `presence:<userId>` on `presence:subscribe`.
Any change to that user's presence map re-emits `presence:list` to that room.
Phones never join it, so a phone cannot enumerate its owner's other devices.

### Link lifecycle

`link:request` validates that the target is the same user, exists, and is not
`busy`, and that the requesting desktop is not already linked (`ALREADY_LINKED` —
the UI offers Disconnect rather than silently stealing the phone). It marks the
device `busy`, mints a `requestId`, and relays `link:incoming` to the phone.

The request expires after **30 s**. On expiry both sides get `link:expired` and
the device returns to the list un-busy. `link:cancel` from the desktop has the
same effect immediately.

On accept, the server creates the `LinkRecord`, emits `link:established` to both,
and immediately pushes the cached `examProblems` — so a phone that links
**mid-exam** gets the problem list without the desktop republishing.

`busy` is set when a request is pending against a device and stays set for the
life of the link. It is cleared — and `presence:list` re-emitted — on decline, on
request expiry or cancel, and on link end from either side. A device that is
still announcing therefore returns to the list as connectable the moment its
link drops.

### Disconnect and reconnect

Both sides get a **30 s grace timer**, not just the desktop as today.

- Desktop disconnects: link is held; if the desktop reconnects and re-subscribes
  within the window it re-attaches. Otherwise `link:ended { reason: 'peer-gone' }`.
- Phone disconnects: presence entry is removed from the list right away (so the
  desktop sees it vanish), but the link is held. A phone that reconnects and
  announces the same `deviceId` inside the window re-attaches: the timer is
  cleared, `phoneSocketId` updated, `link:established` re-sent to the phone so it
  restores its state, and `link:peer-reconnected` sent to the desktop.

The phone grace matters more than it looks. Phones sleep their screens
constantly; without it, pairing dies every time a student glances away.

### Security invariants carried over unchanged

These are load-bearing and must survive the rewrite:

- JWT verification on the handshake (`verifyJwtHs256`), identity read **only**
  from `socket.data.authUserId`, never from an event payload.
- Rejection of companion-scoped tokens (`type === 'companion'` or
  `scope === 'companion'`). `POST /companion/pair` is unauthenticated and mints
  tokens with the same `SECRET_KEY`; without this guard anyone could obtain one
  and authenticate as a real user.
- The 8 MB image ceiling (`MAX_IMAGE_BYTES`) and the 10 MB `maxHttpBufferSize`.
- The CORS allowlist plus the private-network origin regex.
- Exit-on-boot if `REALTIME_JWT_SECRET`/`SECRET_KEY` is unset.

## Desktop

`PairingContext` becomes `ConnectContext`:

```ts
type ConnectStatus = 'idle' | 'connecting' | 'discovering' | 'requesting' | 'linked' | 'error';

{
  status, error,
  devices: DiscoveredDevice[],
  linkedDevice: LinkedDevice | null,
  pendingRequest: { deviceId, requestId, expiresAt } | null,
  latestImage: PairingImagePayload | null,
  refreshDevices(),
  requestLink(deviceId), cancelRequest(), endLink(),
}
```

**Subscription is session-long, not panel-scoped.** The provider connects and
sends `presence:subscribe` as soon as there is an authenticated user and
`REALTIME_AVAILABLE` is true, and stays subscribed until unmount. It has to: the
navbar badge and an inbound `answer:submit` during an exam both need a live
socket whether or not the Settings panel is open. `refreshDevices()` exists only
so the panel can force a re-fetch on open; there is no start/stop of discovery
on the desktop side. Discovery is gated on the *phone* — a device is listed only
while it is announcing.

`latestImage` and the `TEST_ANSWER_IMAGE_EVENT` window dispatch are kept
byte-identical in behaviour. That is what lets `NVOPracticeExamPage` and
`MathVisionPanel` go untouched.

`SettingsConnectionPanel` is rebuilt as the device list:

- **Empty** — "Отвори приложението на телефона си и влез в раздел Свързване."
- **Rows** — device icon, name, relative last-seen, `Свържи` button. Busy devices
  show a disabled button and a "заето" note.
- **Requesting** — "Изчаква потвърждение от <device>…" with a countdown and
  Откажи.
- **Linked** — connected card with the device name and Прекъсни.

`AppNavbar`'s `PairingChip` currently renders `roomCode` with a regenerate
button. It becomes: linked device name as a badge when linked; otherwise a
`Свържи телефон` button calling `useSettings().openSettings()`.

## Phone

`/controller` stays (existing bookmarks) with `/connect` added as an alias. The
existing login gate is unchanged — pairing still requires an account on both
ends, which is what makes account-scoped discovery safe.

Four states:

1. **Visible** — "Компютърът ти може да те види като *iPhone · Safari*", an
   editable nickname, and a live indicator. Mounting announces; unmounting or
   navigating away withdraws. This is exactly the "only appears while on the
   connect section" requirement.
2. **Confirm** — full-screen sheet, "<Desktop> иска да се свърже", Приеми /
   Откажи, with the 30 s countdown.
3. **Connected, idle** — the Kahoot screen. A large check, the device name,
   "Погледни екрана на компютъра", and Прекъсни. Deliberately nothing else.
4. **Connected, exam running** — the problem list. One card per open-response
   problem showing its label (`Задача 17`, from `ActiveTestProblem.label` — not
   the hardcoded English `Problem {id}` used today), a Take Photo button, a
   thumbnail and a check once sent, Retake, and a "3 от 8 изпратени" progress
   pill.

The HEIC and canvas conversion logic in the current `ControllerPage`
(`isImageFile`, `isHeicFile`, `imageToJpegCanvas`, `readFileAsDataUrl`, the
30 s HEIC / 10 s standard timeouts) is carried over as-is. It handles real iOS
behaviour correctly and is not worth rewriting. It moves into
`frontend/src/utils/imageCapture.ts` so the page component stays readable and
the conversion can be unit-tested.

Phone UI copy is Bulgarian throughout, matching the rest of the app.

## NVO integration

The contract is unchanged:

- `NVOPracticeExamPage` calls `publishActiveTestData(openTestProblems)` on start
  and `clearActiveTestData()` on finish.
- `ConnectContext` forwards those to the server as `exam:problems`.
- Inbound `answer:submit` is dispatched as `TEST_ANSWER_IMAGE_EVENT`, which
  `NVOPracticeExamPage` already listens for and writes into `answerImages`.

Only open-response questions are published, as today.

## Known dead path

`emitSendImage` / the `sendImage` event has **no caller**. Nothing on the phone
emits it, so `latestImage` is permanently `null` and `MathVisionPanel`'s
`autoImage` prop never fires. This predates the rehaul.

The plumbing is kept so `MathVisionPanel` keeps its prop and behaviour, but no
phone entry point is added — the idle screen is meant to be empty. Either give it
a phone button or delete the path in a follow-up; it is out of scope here and is
recorded so it is not mistaken for a regression introduced by this work.

## Error handling

| Case | Behaviour |
|---|---|
| No realtime URL configured | `REALTIME_AVAILABLE` false; panel explains, feature disabled |
| Phone not logged in | Existing login gate on `/controller` |
| Requested device vanished | `DEVICE_GONE`; row disappears, desktop shows a transient notice |
| Device already linked elsewhere | `DEVICE_BUSY`; button disabled with a reason |
| Desktop already linked | `ALREADY_LINKED`; UI directs to Disconnect first |
| Request unanswered | 30 s expiry, both sides notified, device un-busies |
| Phone declines | `link:rejected`; desktop shows "Отказано от устройството" |
| Image over 8 MB / conversion failed | Per-problem error, card returns to un-sent |
| Socket drops mid-exam | 30 s grace; sent photos already on the desktop are kept |

## Testing

**`realtime-server/test/`** — new. Node's built-in test runner plus
`socket.io-client` as a devDependency; a `test` script is added to
`realtime-server/package.json`.

- announce then subscribe yields the device in `presence:list`
- request, accept, link established both sides
- request, decline, `link:rejected`, device un-busy
- request expiry after the timeout
- phone disconnect removes presence but holds the link; re-announce re-attaches
- desktop disconnect and reconnect inside the grace window
- **cross-account isolation**: user B never sees user A's devices, and
  `link:request` for a foreign `deviceId` fails
- companion-scoped token rejected at the handshake
- oversized image rejected with `TOO_LARGE`

**Frontend (vitest)** — `ConnectContext` state transitions across the event
sequence, and `utils/imageCapture.ts`.

Commands, per project convention: `cd frontend && npm test`;
`cd realtime-server && npm test`.
